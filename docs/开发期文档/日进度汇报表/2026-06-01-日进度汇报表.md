### 4. 梳理 AI 文件预处理方案

结合后续真实 AI 评价需求，明确当前建议：

```text
Java 侧负责上传和调度。
Py 侧负责文件解析、压缩包展开、DOCX 结构化抽取、图片 OCR 和可选渲染。
```

队友反馈：

- 如果只是读取 DOCX，当前已完成 DOCX 转 JSON。
- PDF 路线主要是 `DOCX -> PDF -> 图片`，用于检查或修改文档格式。

整理后的共识：

- `DOCX -> JSON` 作为 AI 评价主输入。
- `DOCX -> PDF -> 图片` 作为格式/版式检查辅助能力。
- LibreOffice 在 Linux 上转换 DOCX 可能产生排版误差，因此不应作为唯一评分依据。
- PDF/图片渲染失败时，不应阻断 AI 评价主流程。

### 5. 明确 Py 侧后续建议字段

建议 Py 侧预处理结果增加：

```json
{
  "renderStatus": "ok / degraded / failed",
  "renderEngine": "libreoffice / word / onlyoffice / none",
  "renderWarnings": []
}
```

状态含义：

- `ok`：高保真渲染成功，例如学生提交原始 PDF，或后续接入可信转换服务。
- `degraded`：LibreOffice 转换成功，但版式可能存在误差。
- `failed`：转换失败，但结构化文本、表格、图片 OCR 仍然返回。
- `none`：没有执行渲染。

### 6. 明确 AI 评价降级策略

建议后续 AI prompt 根据 `renderStatus` 调整：

- `ok`：可以参考版式、分页、页面布局和截图。
- `degraded`：版式图片仅作为辅助参考，不应因为分页、对齐、字体差异重扣分。
- `failed`：不评价分页、对齐和页面版式，只评价内容、结构、表格、代码和 OCR 文本。
