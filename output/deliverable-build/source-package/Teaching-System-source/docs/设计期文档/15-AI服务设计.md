# 15-AI 服务设计

说明 `ai-service/` 的设计意图、Java 调用方式、Python 内部架构和当前完成度。

## Java 侧使用

### 当前模式：FakeAIService（已实现）

```
Java EvaluationService
  → AIService.evaluate(AIEvalRequest { studentName, fileName })
    → FakeAIService 返回硬编码 EvaluationResult（aiScore=82.50）
```

无需启动 Python，`mvn spring-boot:run` 即走通全流程。用于离线演示和日常开发。

### 真实 AI 模式：RealAIService（已实现）

当前流程：

```
Java EvaluationService
  → DelegatingAIService.evaluate(WorkSubmission, AIEvalRequest)
    → app.ai.real.enabled=true 时调用 RealAIService
    → RestTemplate POST http://127.0.0.1:8000/api/evaluate/real
      → Python FastAPI 返回 { aiScore, aiIssues, aiComment, status }
```

Java 侧已完成：

1. `DelegatingAIService` 统一对外实现 `AIService`
2. `RealAIService` 使用 `RestTemplate` 以 multipart 方式调用 Py `/api/evaluate/real`
3. 配置项为 `app.ai.real.enabled`、`app.ai.real.endpoint-url` 和超时参数
4. 真实 AI 调用失败时自动降级到 `FakeAIService`

### 真实文件上传 + 预处理（已实现）

当需要上传真实 DOCX 文件并走预处理管线时，Java 侧需调用 `POST /api/evaluate/real`：

```
multipart/form-data: file=report.docx, studentName=张三
→ Python 预处理 → DeepSeek 评分 → 返回 aiScore/aiIssues/aiComment
```

Java 侧已完成：

1. `POST /api/submissions/upload` 保存真实文件到磁盘
2. `PreprocessClient` 可配置调用 Py `/api/preprocess`
3. `RealAIService.evaluate(WorkSubmission, AIEvalRequest)` 使用已保存文件调用 Py `/api/evaluate/real`
4. 第 11 天已确认真实 AI 能返回 `aiScore/aiIssues/aiComment`

## Python 侧架构

### 服务入口

```
ai-service/
├── .env                   # 环境变量（gitignored，含 DEEPSEEK_API_KEY 等）
├── config.py              # 集中配置（自动加载 .env + 环境变量覆盖）
├── start.bat              # Windows 一键启动
├── start.sh               # Linux 一键启动
├── requirements.txt       # FastAPI + python-docx + PyMuPDF + EasyOCR + patool
├── DocxConv/              # 主服务模块（FastAPI，端口 8000）
│   └── src/docxconv/
│       ├── server.py          # 全部 HTTP 端点（预处理 + AI 评分）
│       ├── converters/        # DOCX 转换管线
│       │   ├── json.py        #   python-docx → 结构化 JSON
│       │   ├── img.py         #   LibreOffice + PyMuPDF → 逐页图片
│       │   ├── pandoc_img.py  #   Pandoc + WeasyPrint → 逐页图片
│       │   └── extract_images.py  # 提取内嵌图片
│       └── __main__.py        # CLI：python -m docxconv serve|to-json|to-images
├── Evaluator/             # AI 评分模块（独立包）
│   └── src/evaluator/
│       └── deepseek.py        # DeepSeek API 调用，参数全部来自 config.py
├── ScreenshotProc/        # OCR 模块
├── ArchiveProc/           # 压缩包解压模块
└── test/                  # 测试数据（不入仓库）
```

### 预处理管线

```
POST /api/preprocess  (file: .docx)
  │
  ├── convert_obj(docx)           → content   （python-docx 解析，不依赖外部进程，必定成功）
  ├── extract_images_metadata()   → images    （内嵌图片列表）
  └── 检测 LibreOffice
        ├── 存在 → docx_to_pdf → try render
        │     ├── 成功 → renderStatus=degraded, renderEngine=libreoffice
        │     └── 失败 → renderStatus=failed, renderEngine=libreoffice
        └── 不存在 → renderStatus=failed, renderEngine=none
```

渲染失败不阻断：`content` 来自 `python-docx`（纯内存操作），无论 LibreOffice 是否就绪都正常返回。

### renderStatus 设计决策

| 状态 | 含义 | 触发条件 |
|---|---|---|
| `ok` | 渲染质量无问题 | **当前不使用**。LibreOffice 不是 Word，排版有差异，用 `degraded` 诚实标注 |
| `degraded` | 渲染可用但非官方引擎 | LibreOffice 转 PDF 成功 |
| `failed` | 渲染不可用 | LibreOffice 不存在或转换抛出异常 |
| `none` | 未尝试渲染 | 仅做 DOCX 结构解析，跳过页面渲染 |

## MVP API 端点

当前阶段仅暴露 4 个端点。`/convert/*`、`/extract/*` 底层模块保留但暂不挂载为 HTTP 端点。

| 端点 | 方法 | 入参 | 返回 | 状态 |
|---|---|---|---|---|
| `/api/health` | GET | — | `{status, version, modules, features}` | 已实现 |
| `/api/health/deepseek` | GET | — | `{connected, model, latencyMs, detail}` | 已实现 |
| `/api/preprocess` | POST | `file` (任意) | `{fileType, originalFilename, extractedText, warnings}` | 已实现 |
| `/api/evaluate` | POST | `studentName` (query) | 硬编码评分 (82.5) | 已实现（假 AI，兼容 Java） |
| `/api/evaluate/real` | POST | `file` + `studentName` (query) | 预处理结果 + `aiScore/aiIssues/aiComment` | 已实现（真实 DeepSeek 评分） |

### `/api/preprocess` 支持的文件类型

| 类型 | 后缀 | 提取方式 | 说明 |
|---|---|---|---|
| 纯文本/代码 | .txt .cpp .java .py .md 等 30+ | 直接读取（自动检测 UTF-8/GBK/UTF-16） | — |
| DOCX | .docx | python-docx 结构解析 → 纯文本 | 附带 `structuredContent`（标题/段落/列表/表格） |
| DOC (旧版) | .doc | 尝试按 docx 解析 | 可能失败，返回 warning 建议转为 .docx |
| PDF | .pdf | PyMuPDF 提取文本 | 扫描件 PDF 无法提取，返回 warning |
| XLSX/XLS | .xlsx .xls | openpyxl 逐工作表提取 | 只读模式，提取含公式单元格的缓存值 |
| PPTX/PPT | .pptx .ppt | python-pptx 逐幻灯片提取 | 含表格内文本 |
| 图片 (OCR) | .png .jpg .jpeg .bmp .webp | EasyOCR 识别 → 按阅读顺序排列 | 识别结果可能有错字，附 warning |
| 压缩包 | .zip .tar .rar .7z | 解压后递归提取文本文件 | 仅提取可读文本文件，二进制文件跳过 |

### `/api/preprocess` 统一返回格式

```json
{
  "fileType": "docx",
  "originalFilename": "report.docx",
  "extractedText": "全文纯文本...",
  "warnings": []
}
```

注：`.docx` 额外返回 `structuredContent` 字段，保留标题层级和文档结构供后续格式审核使用。当前 AI 不使用此字段。`.xlsx`/`.pptx` 暂不返回结构化数据（仅提取纯文本），后续如有需求可扩展。

### `/api/health` 健康检查规范

#### 返回格式

```json
{
  "status": "ok",
  "version": "0.7.0",
  "modules": {
    "docxconv": "0.5.0",
    "screenshotproc": "0.1.0",
    "archiveproc": "0.1.0",
    "evaluator": "0.1.0"
  },
  "features": {
    "libreoffice": { "available": true, "detail": "" },
    "pandoc": { "available": true, "detail": "" },
    "deepseek": { "available": true, "detail": "" },
    "easyocr": { "available": false, "detail": "EasyOCR 未安装，截图 OCR 不可用" },
    "archive_7z": { "available": true, "detail": "" },
    "archive_rar": { "available": false, "detail": "rarfile 或 unrar 未安装，RAR 解压不可用" }
  }
}
```

#### status 判定逻辑

| status | 条件 |
|---|---|
| `ok` | 全部 6 项依赖均可用 |
| `degraded` | 核心 3 项（libreoffice / pandoc / deepseek）均可用，但部分可选依赖缺失 |
| `unavailable` | 核心依赖中任一项不可用，服务无法提供完整功能 |

#### 各 features 字段

| 字段 | 重要性 | 检查方式 | 不可用时影响 |
|---|---|---|---|
| `libreoffice` | 核心 | `SOFFICE_PATH` 指向的文件是否存在 | DOCX 页面渲染不可用（结构化提取仍可用） |
| `pandoc` | 核心 | `PANDOC_PATH` 是否非空 | 备用渲染管线不可用 |
| `deepseek` | 核心 | `DEEPSEEK_API_KEY` 是否已配置 | AI 评分不可用 |
| `easyocr` | 可选 | `import easyocr` 是否成功 | 截图 OCR 不可用 |
| `archive_7z` | 可选 | `import py7zr` 是否成功 | 7z 压缩包解压不可用 |
| `archive_rar` | 可选 | `import rarfile` 且 `rarfile.tool_setup()` 返回 True | RAR 解压不可用 |

#### 设计决策

- **不做 DeepSeek 实时连通性探测**：`/api/health` 是高频端点，每次发真实 API 调用会消耗 token 配额并增加响应延迟。仅检查 API key 是否已配置。如需验证 DeepSeek 连通性，使用单独的深度检查端点（待实现）。
- **EasyOCR 只做 import 检查**：不加载模型（模型加载耗时且占内存），仅验证包是否已安装。
- **版本号硬编码**：与各子模块 `pyproject.toml` 中的版本保持一致，后续版本升级时需同步更新。

### `/api/health/deepseek` 深度检查

独立的 DeepSeek API 连通性探测端点，发起真实调用（`max_tokens=1`，消息内容为 `"ping"`），测量往返延迟。

#### 返回格式

```json
// 连接正常
{ "connected": true,  "model": "deepseek-v4-pro", "latencyMs": 847, "detail": "" }

// API key 未配
{ "connected": false, "model": "deepseek-v4-pro", "latencyMs": 0,   "detail": "DEEPSEEK_API_KEY 未配置" }

// 网络/鉴权失败
{ "connected": false, "model": "deepseek-v4-pro", "latencyMs": 1523, "detail": "API 调用失败: Connection error" }
```

#### 与 `/api/health` 的差异

| 端点 | 检查方式 | 消耗配额 | 适用场景 |
|---|---|---|---|
| `/api/health` | 仅检查 `DEEPSEEK_API_KEY` 是否配置 | 无 | 负载均衡探活、高频健康检查 |
| `/api/health/deepseek` | 发起真实 API 调用 | 每次 ~1 token | 故障排查、运维诊断 |

### `deepseek.py` 与 `config.py` 的关系

- `deepseek.py` 通过 `import config` 读取所有参数，不再硬编码

- `_get_client()` 使用 `config.DEEPSEEK_API_KEY` 创建 OpenAI 客户端，全局单例延迟初始化

### `/api/evaluate/real` 行为变更

- 之前：预处理管线返回 `extractedText` + `aiScore=null`（AI 占位，未实际调用）
- 现在：`file → preprocess → evaluate_content(extractedText, studentName) → JSON`
- 失败兜底：空文本返回 aiScore=0 + 提示信息；API 异常返回 503；JSON 解析失败返回 aiScore=0 + 原始输出片段

## 5. 多类型文件测试报告

以下测试通过 `POST /api/evaluate/real`（multipart/form-data）执行，覆盖 5 种场景。

### 测试环境

- 服务：`python -m docxconv serve`，端口 8000
- 调用方式：`curl -F "file=@<path>" -F "studentName=<name>"`
- DeepSeek Model：`deepseek-chat`，temperature=0.3，max_tokens=800

### 样本 1：简单 DOCX（SimpleTest.docx）

**文件内容：** 117 字，含 3 级标题、无序列表、有序列表、正文段落。

```
# 标题1
正文1
## 标题2
* 无序表1、2
- 有序表1、2、3
- 没有遵循格式的有序表1、2、3
### 标题3
正文2
```

**AI 输出：**

- aiScore：68
- aiIssues：
  1. 内容过于简略，缺乏深度和细节，字数不足
  2. 结构混乱，无序列表和有序列表混用，且有序列表未使用数字序号
  3. 格式不规范，有序列表应使用数字加英文句点，而非连字符
- aiComment：内容较为简单，结构上存在混乱，尤其是列表格式不统一。建议增加论述深度和具体例子，同时规范使用有序列表的编号方式。

**结论：** DOCX 结构化解析正常，AI 能识别列表格式混用并给出针对建议。

### 样本 2：复杂 DOCX（Comprehensive.docx）

**文件内容：** 含标题、有序列表、5 行学生信息表格（含身份证号等敏感字段），以及一张嵌入图片（1267x756 PNG）。

**预处理输出（文本提取 + 图片 OCR）：**

- 文档文本：596 字（标题 + 列表 + 表格行内拼接）
- 图片 OCR：718 字（从嵌入图片识别出的架构图文字、中英文模块名）
- 合并后总文本长度：1314 字
- warning：`["文档中的图片内容由 OCR 识别，可能存在错字"]`

**AI 输出：**

- aiScore：65
- aiIssues：
  1. 内容深度不足，多为列表和表格，缺乏明确的论述和分析段落
  2. 结构不清晰，未划分明确的章节标题和逻辑段落
  3. 格式不规范，列表项使用连字符而非项目符号，表格内容超出范围
- aiComment：作业内容较为简单，但缺乏实质性的论述和分析。建议围绕表格中的数据展开更深入的讨论，明确章节结构，规范格式。希望下次能提交更充分的内容。

**结论：** python-docx 正确解析混合内容（标题+列表+表格）；内嵌图片通过 `extract_images()` + EasyOCR 成功提取文字，OCR 结果追加到 `extractedText` 尾部并添加 warning。AI 评分仅基于文档文本（596 字），图片 OCR 内容作为补充信息一并提交。

### 样本 3：文本文件（CodeText-txt.txt）

**文件内容：** 53 字，C++ 空 main 函数。

```cpp
#include <iostream>
int main() { return 0; }
```

**AI 输出：**

- aiScore：60（基准分）
- aiIssues：1. 作业内容仅有一个空的 main 函数，没有实现任何功能或逻辑；2. 完全没有体现对课程内容的理解和应用
- aiComment：作业仅提供了一个空的程序框架，请根据作业要求补充完整内容。

**结论：** `.txt` 文件作为 `text` 类型解析，编码自动检测正常，AI 发现内容空洞。

### 样本 4：代码文件（CodeText.cpp）

**文件内容：** 与样本 3 相同（53 字，空 main 函数）。

**AI 输出：** 与样本 3 一致（aiScore=60，同样的 issues 和 comment）。

**结论：** `.cpp` 属于 `TEXT_EXTENSIONS`，按文本处理。编码检测（UTF-8）正常，AI 评分结果与 .txt 一致，文件类型标签正确为 `text`。

### 样本 5：错误处理

| 场景 | 请求 | 响应 | 状态码 |
|---|---|---|---|
| 缺少 file 参数 | `-F "studentName=x"` | `{"detail":[{"type":"missing","loc":["body","file"],"msg":"Field required"}]}` | 422 |
| 空请求体 | `-X POST`（无参数） | 同上 | 422 |
| 不存在的文件路径 | curl 本地报错 | curl: Can't open... | N/A（curl 层拦截，未到达服务） |

**结论：** FastAPI 的 `UploadFile = File(...)` 自动校验，缺少文件参数返回标准 422。不存在的文件在 curl 层面报错，不进入服务端逻辑。

### 评分总结

| 样本 | 类型 | 文本长度 | aiScore | AI 判断依据 |
|---|---|---|---|---|
| SimpleTest.docx | docx | 117 | 68 | 内容简略，列表格式混乱 |

## 6. Swagger "Try it out" 文件上传指南

浏览器安全策略决定了文本输入框里的路径字符串不会被当作文件内容发送——手动打字路径只会把字符串 `"D:/xxx/file.docx"` 传给服务端，收到 `Expected UploadFile, received: str` 的 422 错误。

| 操作 | 结果 |
|---|---|
| 手动在输入框里打字写路径 | 422 `Expected UploadFile, received: str` |

**curl 用法（推荐，最可靠）：**

```bash
# 预处理
curl -F "file=@path/to/report.docx" http://localhost:8000/api/preprocess

# 真实 AI 评分
curl -F "file=@path/to/report.docx" -F "studentName=张三" http://localhost:8000/api/evaluate/real
```

**常见错误排查：**

| 错误信息 | 原因 | 解决 |
|---|---|---|
| `Expected UploadFile, received: str` | 手动打字文件路径而非用文件选择器 | 点 file 字段右侧的「选择文件」按钮 |
| `Failed to fetch` | 跨域：Swagger UI 所在 origin 不能直连 AI 服务 | 本地用 `localhost:8000/docs`；线上通过 nginx 代理 |
| `Field required` | 未选择文件或未传 file 参数 | 选择文件后重试 |
| `curl: Can't open` | 文件路径不存在 | 检查路径拼写和文件是否存在 |

## 9. `/api/evaluate/real` 降级保险

当 DeepSeek API 调用失败（`RuntimeError`）时，`/api/evaluate/real` 不再返回 503 错误，而是自动降级为默认评分（`aiScore=82.50`），并在 `warnings` 中附加降级原因。

- **降级触发条件**：`evaluate_content()` 抛出 `RuntimeError`（API key 未配、网络不通、DeepSeek 返回异常、JSON 解析失败等）
- **降级行为**：返回 200 + 预处理数据 + 默认评分（`aiScore=82.50`）+ `status=1`，`warnings` 中追加 `"DeepSeek 评分失败，已降级为默认评分: ..."`
- **日志**：通过 `logger.warning` 记录降级事件

这与 Java 侧 `DelegatingAIService` 的降级逻辑形成双重保险——Py 侧先在服务内部兜底，Java 侧的 `catch (RuntimeException)` 作为最外层保护。

## 10. 多维度评分体系（Rubric）

### 评分维度

评分从单一总分升级为**多维度加权评分**。每次评估按一组评分维度分别打分，`aiScore` 为各维度分数按权重加权求和。

默认维度按学科类型预设：

| 学科 | 维度 |
|---|---|
| code（代码） | 代码质量(35%)、功能完整性(35%)、文档与说明(15%)、创新与优化(15%) |
| document（文档） | 内容完整性(35%)、逻辑与结构(30%)、格式规范(20%)、表达与创新(15%) |
| design（设计） | 方案合理性(35%)、文档规范性(30%)、技术深度(20%)、创新与可行(15%) |
| general（通用） | 完成度(40%)、正确性(30%)、规范性(30%) |

### 自定义维度

`/api/evaluate/real` 和 `/api/evaluate/stream` 支持可选参数 `rubric`（JSON 字符串），允许教师自定义评分维度：

```json
{"dimensions":[{"name":"代码质量","weight":0.4,"description":"..."},{"name":"功能实现","weight":0.6,"description":"..."}]}
```

约束：1-8 维度、名称唯一、权重和 1.0 ± 0.01。

### `/api/evaluate/real` 响应变更

新增 `dimensionScores` 字段：

```json
{
  "aiScore": 87.00,
  "aiIssues": "1. ...",
  "aiComment": "...",
  "dimensionScores": [
    {"name": "代码质量", "score": 88, "comment": "命名规范良好"},
    {"name": "功能完整性", "score": 86, "comment": "核心功能完成"}
  ]
}
```

### Java 侧持久化

- `EvaluationResult` 新增 `dimensionScores` TEXT 列，以 JSON 字符串存储
- `RealAIService` 解析 Py 返回的 `dimensionScores` 并持久化
- FakeAIService、ExportRow、ExportService 同步更新
- `schema.sql` 同步新增 `dimension_scores` 列

## 12. API 重试机制

DeepSeek API 调用新增指数退避重试：

- 默认 3 次，基础延迟 1s，指数因子 2，最大延迟 10s
- 流式评分仅重试连接建立，流开始后不重试

## 13. 流式评分（SSE）

### 新端点

`POST /api/evaluate/stream` — 以 Server-Sent Events 流式推送评分过程。

### SSE 事件契约

| 事件 | 时机 | payload |
|---|---|---|
| `start` | 预处理完成 | `{"subjectType":"code","dimensions":[...]}` |
| `reasoning` | Thinking trace 片段到达 | `{"delta":"..."}` |
| `content` | 评分 JSON token 到达 | `{"delta":"{\n "}` |
| `result` | 流结束，JSON 解析成功 | 完整评分结果 JSON |
| `error` | 任何失败 | `{"message":"...","code":"..."}` |
| `done` | 流终止 | `{}` |

前端使用 `fetch` + `ReadableStream` 消费（不能用 `EventSource`，因为需要 POST 上传文件）。

### 实现要点

- `evaluate_stream()` 生成器在 `deepseek.py` 中，`_format_sse()` 格式化 SSE 帧
- `StreamingResponse` + `X-Accel-Buffering: no` 防 nginx 代理缓冲
- `stream_options={"include_usage": True}` 获取 token 统计

## 16. 流式评分结果持久化端点

### 新 Java 端点

`POST /api/submissions/{submissionId}/evaluation-result` — 接收流式评分或外部计算好的 AI 结果，直接写入 `evaluation` 表，**不触发新的 AI 调用**。

请求体：
```json
{
  "aiScore": 89.00,
  "aiIssues": "1. ...",
  "aiComment": "...",
  "dimensionScores": "[{\"name\":\"代码质量\",\"score\":88,\"comment\":\"良好\"}]"
}
```

`aiScore` 必填（0-100），其余字段可选。新建或更新已有记录，保留 `teacherScore`/`teacherComment`。

### 背景

流式评分 (`/api/evaluate/stream`) 是前端直连 Python，结果仅在前端本地状态，未持久化到数据库。旧的非流式评分 (`POST /api/submissions/{id}/evaluate`) 走 Java → Python → Java 保存，自动持久化。此端点补上流式路径的持久化缺口。
